# 10 — استراتيجية العمل دون اتصال والمزامنة

## 10.1 المبدأ الحاكم

> **الجهاز يسجل ما حدث (Commands/Facts). الخادم يقرر ما يعنيه (State).**

لا نزامن "حالة" الكيانات من الجهاز إلى الخادم (لا `PUT workorder {state: CLOSED}`). الجهاز يرسل **أوامر بما فعله المستخدم**، والخادم يطبقها على آلة الحالات. هذا يلغي معظم مشاكل الـ Overwrite من جذورها.

وقاعدتان لا استثناء لهما:
1. **لا يُفقد دليل ميداني أبدًا.** حتى لو رُفض الأمر، يُحفظ في الحجر (Quarantine) لقرار بشري.
2. **لا يُلغي الجهاز قرار الخادم أبدًا.** إذا تعارض ما فعله الجهاز مع حالة الخادم، الخادم يربح والتعارض يظهر للإنسان.

## 10.2 ما يعمل دون اتصال (MVP)

| الوظيفة | دون اتصال | ملاحظة |
|---|---|---|
| عرض مهامي والأصول المرتبطة | ✅ | تُحمّل مسبقًا عند آخر مزامنة |
| مسح QR وحل الملصق | ✅ للأصول المحلية | ذاكرة محلية لأصول منطقة الفني (عدة آلاف سجل خفيف) |
| التصوير والأدلة | ✅ | |
| التشخيص، قائمة الفحص، المواد من العهدة | ✅ | رصيد العهدة المحلي تقديري |
| تقديم أمر العمل | ✅ (يُصف) | الحالة المحلية "مُرسل — بانتظار المزامنة" |
| تسجيل أصل جديد (مسح) | ✅ | |
| تأكيد استلام عهدة | ✅ | |
| جولة تفقد وإنشاء بلاغات | ✅ | |
| الخريطة | ⚠️ جزئي | البلاطات المخزنة مؤقتًا فقط؛ القوائم تعمل دائمًا بدون خريطة |
| استلام مهام جديدة | ❌ | يتطلب اتصالًا |
| مراجعة وإغلاق (المشرف) | ❌ | الويب فقط — قرارات الاعتماد تتطلب حالة خادم حديثة |

## 10.3 مكونات محرك المزامنة على الجهاز

```
┌──────────────────────── Mobile ────────────────────────┐
│  UI  ─►  Local Domain (optimistic local state)         │
│             │                                          │
│             ▼                                          │
│  Outbox (SQLite, encrypted): ordered commands          │
│   {command_id(UUIDv7), type, payload, payload_hash,    │
│    entity_ref, depends_on[], device_time, elapsed_ms,  │
│    boot_id, status[PENDING|SENT|ACK|REJECTED]}         │
│             │                                          │
│  Media Queue: files + sha256 + upload progress          │
│             │                                          │
│  Sync Worker (WorkManager): on connectivity / periodic  │
│   1) push commands (batch, in order)                   │
│   2) upload media (resumable, chunked, Wi-Fi pref.)    │
│   3) pull changes since cursor                         │
└────────────────────────────────────────────────────────┘
```

- **الترتيب:** الأوامر تُرسل بترتيب إنشائها لكل كيان (`depends_on` يضمن أن `AddEvidence` لا يسبق `Arrive`).
- **Idempotency:** `command_id` مفتاح فريد على الخادم. إعادة الإرسال ← `DUPLICATE` بنفس النتيجة الأصلية.
- **الوسائط منفصلة عن الأوامر:** الأمر يحمل الـ hash فقط (صغير، يصل بسرعة حتى على شبكة ضعيفة)؛ الصور تُرفع لاحقًا عبر روابط رفع موقعة مباشرة إلى S3 (Multipart، قابلة للاستئناف).
- **ضغط الصور:** إعادة ترميز على الجهاز إلى JPEG بجودة ~80% وحد أقصى 2048px للضلع الأطول ← عادة 300–700KB. **الـ hash يُحسب على الملف النهائي المضغوط** (ما سيُرفع فعلًا).
- **إعدادات:** "رفع الصور عبر Wi-Fi فقط" اختياري؛ الأوامر ترسل دائمًا عبر أي شبكة.

## 10.4 معالجة الأوامر على الخادم

```
for each command in batch (in order):
  if exists(command_id)                 → return stored result (DUPLICATE)
  if device revoked / user disabled     → QUARANTINE (reason: DEVICE_REVOKED) 
  verify payload_hash
  load aggregate (e.g., WorkOrder) 
  authorize(actor, command, aggregate)  → REJECT or QUARANTINE (see matrix)
  apply to state machine:
     valid transition                   → APPLY (events + audit in one tx)
     conflict                           → resolution matrix below
  record sync_commands row with result
return per-command results + new server cursor
```

## 10.5 مصفوفة حل التعارضات (Domain-level)

| الحالة على الخادم عند وصول أوامر الفني | ماذا نفعل | لماذا |
|---|---|---|
| أمر العمل **أُعيد إسناده** لفني آخر بينما الأول كان يعمل دون اتصال | الأدلة والمواد تُقبل وتُربط بأمر العمل مع علامة `SUBMITTED_BY_NON_ASSIGNEE` + إشعار المشرف؛ **لا** تُطبق انتقالات الحالة (Submit) تلقائيًا | العمل الميداني حدث فعلًا؛ المواد استُهلكت فعلًا — لا نفقدها. القرار للمشرف. |
| أمر العمل **أُلغي** | الأوامر ← QUARANTINE؛ المشرف يقرر (إعادة تفعيل / ربط بأمر آخر / قبول مع إغلاق) | لا يُتجاهل عمل حدث |
| **الأصل شُطب أو تحت التحقيق** | القبول مع Flag عالٍ | |
| **فنيان** قدّما لنفس أمر العمل (رئيسي ومساعد) | الانتقالات تُقبل من الرئيسي فقط؛ أدلة المساعد تُضاف | Single writer للحالة |
| تسجيل أصل **بنفس الملصق** من مسجلين مختلفين | الأول يربح؛ الثاني ← QUARANTINE + Flag (ملصق مكرر = إما خطأ أو نسخ) | |
| استهلاك **يتجاوز رصيد العهدة** | APPLY + Flag | الواقع الميداني أولًا، ثم المراجعة |
| أمر **يسبق اعتماده الزمني حدثًا على الخادم** (مثلًا "بدء العمل" بتاريخ قبل الإسناد) | APPLY + Flag `TEMPORAL_INCONSISTENCY` | غالبًا ساعة خاطئة |
| جهاز **مُلغى** يرسل بيانات | QUARANTINE كامل؛ لا تطبيق | قد يكون مسروقًا |
| أمر غير مصرح (فني يحاول مهمة ليست له أبدًا) | REJECT + حدث أمني | |

**الحجر (Quarantine):** طابور في واجهة المشرف/المدقق مع الأمر الأصلي والسياق وخيارات القرار. كل قرار حدث تدقيق.

**التعديلات المتزامنة على الويب** (مثلًا مشرفان يعدلان نفس الشيء): التزامن المتفائل (`expected_version`) ← الثاني يحصل على `409 Conflict` مع الحالة الحالية ويعيد المحاولة. لا دمج تلقائي للحقول.

## 10.6 الوقت دون اتصال (Trusted Time)

ساعة الجهاز قابلة للتلاعب، خاصة دون اتصال. نسجل لكل حدث:

| القيمة | المصدر | قابلة للتلاعب؟ |
|---|---|---|
| `device_time` | ساعة الجهاز | نعم |
| `elapsed_ms` | `SystemClock.elapsedRealtime()` (منذ الإقلاع، لا يتأثر بتغيير الساعة) | لا (يتصفر عند إعادة التشغيل) |
| `boot_id` | معرف جلسة الإقلاع | — |
| `server_time` عند الاستلام | الخادم | لا |

**عينات المعايرة:** عند كل اتصال ناجح، الجهاز يسجل الزوج `(server_time, elapsed_ms, boot_id)`.

**الحساب:** إذا كان لدينا عينة معايرة لنفس `boot_id`:
`estimated_time = server_time_at_sample + (event.elapsed_ms − sample.elapsed_ms)`
هذا الوقت **لا يتأثر بتغيير ساعة الجهاز**.
إذا أُعيد تشغيل الجهاز دون اتصال (لا عينة للـ boot_id الجديد): نستخدم `device_time` ونعلّم `time_confidence = LOW`، ونتحقق من الاتساق (ليس قبل آخر وقت موثوق، وليس بعد وقت الاستلام).

**الإشارات:**
- `|device_time − estimated_time| > 5 دقائق` ← `CLOCK_SKEW` (معلومة؛ تتحول لـ Flag إذا تكررت أو إذا غيّرت النتيجة — مثل SLA).
- حدث بتاريخ بعد استلامه على الخادم ← مستحيل ← Flag.

## 10.7 حدود العمل دون اتصال

- **حد أقصى تحدده السياسة** (تصحيح: القيمة المبدئية للتجربة 24 ساعة، قابلة للتهيئة وليست ثابتة في الكود — انظر `docs/lean-pilot/05-byod-offline-security.md`) دون مزامنة ناجحة ← التطبيق يطلب اتصالًا لمتابعة العمل الجديد (يمكن دائمًا إكمال وإرسال المهام الجارية وتصوير الأدلة — لا نمنع الفني من إنهاء عمل بدأه).
- الرموز (Tokens): Access قصير (15 دقيقة) + Refresh مرتبط بالجهاز (Device-bound) بصلاحية مطلقة 7 أيام. دون اتصال، التطبيق يعمل بجلسة محلية محمية بالقفل المحلي حتى الحد أعلاه.
- **الأوامر المنشأة دون اتصال لمدة طويلة** (> 24 ساعة بين الإنشاء والوصول) تحمل علامة للمراجع — معلومة، ليست Flag.

## 10.8 السحب (Pull) — ما يُنزّل للجهاز

- المهام المسندة + الأصول المرتبطة + الأصول في منطقة الفني (نسخة خفيفة: id, code, tag, type, location, status).
- قوالب الفحص وقوائم التشخيص والأصناف.
- رصيد العهدة (من الخادم — يستبدل التقدير المحلي).
- **لا** ينزل: صور أصول أخرى بالحجم الكامل، بيانات موظفين آخرين، الإشارات.
- آلية: `cursor` (آخر `change_seq`) لكل نوع؛ التغييرات فقط.

## 10.9 أمن البيانات على الجهاز

- قاعدة SQLite مشفرة (SQLCipher)؛ المفتاح في Android Keystore.
- الصور المخزنة محليًا في مساحة التطبيق الخاصة (لا تظهر في معرض الصور)، مشفرة.
- حذف محلي للصور بعد تأكيد الخادم `HASH_OK` + مهلة (مثلًا 7 أيام) — يوفر المساحة على الأجهزة الضعيفة.
- عند إلغاء الجهاز: الخادم يرفض كل مزامنة وكل إجراء من هذا الجهاز. **لا نعتمد على مسح بيانات الهاتف** (هاتف شخصي بلا MDM) — انظر [17](17-decisions-and-syria-context.md) و`docs/lean-pilot/05-byod-offline-security.md`.

## 10.10 اختبار المزامنة

محاكي سيناريوهات تلقائي في CI: عشرات السيناريوهات (إعادة إسناد أثناء عدم الاتصال، إلغاء، ساعة معدلة، إعادة تشغيل، شبكة تنقطع أثناء رفع، أوامر مكررة، ترتيب معكوس، جهاز ملغى) — كل سيناريو يتحقق من: لا فقدان أدلة، لا تجاوز لقرار خادم، الحالة النهائية المتوقعة، أحداث التدقيق. انظر [14](14-testing-strategy.md).
