# 16 — نطاق MVP، المراحل، تعريف الإنجاز، المخاطر، وما لن يُبنى

## 16.1 نطاق MVP (= Phase 0 + Phase 1)

### داخل النطاق

| # | من القائمة الأصلية | التعديل |

| 1 | Users + Roles | + SoD ثابت وديناميكي + تسجيل الأجهزة + Break Glass أساسي |

| + | **جديد** | البلاغات + التأكيد + جولة التفقد الليلية · Four-Eyes عام · التدقيق العشوائي (مكتبي) · الحجر |

**لماذا Offline إلزامي في MVP وليس اختياريًا؟** لأنه يغير معمارية التطبيق الميداني من الأساس (أوامر لا حالة، UUID على الجهاز، ترتيب، hash). إضافته لاحقًا = إعادة كتابة التطبيق الميداني ونموذج الـ API. رخيص الآن، باهظ لاحقًا.

**لماذا التدقيق العشوائي في MVP بدل Phase 2؟** شكله المكتبي بسيط (مهمة ليلية + طابور)، وهو **الأداة الوحيدة لقياس دقة القواعد** في التجربة. بدونه لا نعرف إن كانت الإشارات صحيحة.

## 16.2 المراحل

> التقديرات الزمنية تفترض فريقًا من: قائد تقني/Backend، مطور Backend، مطور Flutter، مطور Web، مصمم UX (جزئي)، مختبر QA (جزئي)، مالك منتج من جهة البلدية (جزئي — **إلزامي**). تُراجع بعد Phase 0.

### PHASE 0 — Foundation (≈ 5–7 أسابيع)

**الهدف:** كل ما يصعب تغييره لاحقًا، ولا شيء غيره.

| المسار | المخرجات |
|---|---|
| قرارات | ADRs للقرارات في [08](08-architecture-and-technology.md) — **بعد** الإجابة على الأسئلة المفتوحة (16.5) |
| اكتشاف | زيارة ميدانية: مرافقة فريق إنارة ليلًا ونهارًا · مقابلات: فنيون، مشرف، مخزن · جمع: قوائم الأعطال الحالية، أصناف المخزون، النماذج الورقية · **خط أساس** (زمن الإصلاح الحالي، جرد افتتاحي مخطط) |
| تصميم | نموذج قابل للنقر للتطبيق الميداني + شاشة المراجعة؛ **اختبار مع 3–5 فنيين** · قاموس المصطلحات |
| المستودع | الهيكل في [08 §8.6](08-architecture-and-technology.md#86-هيكل-المستودع-monorepo) · CI (build, tests, lint, secrets & dependency scan) · Conventional commits |
| Backend | Host + BuildingBlocks · Identity (Keycloak، المستخدمون، الأدوار، الإسناد، SoD الثابت، الأجهزة) · Organization (الوحدات، المناطق) · **Audit كامل** (حدث في نفس المعاملة، سلسلة، Trigger، checkpoint، `chain-verifier`) · Outbox + Worker · Idempotency · Authorization framework + اختبار المصفوفة المولد · Approvals (المحرك العام) |
| Mobile | الهيكل · تسجيل الدخول + تسجيل الجهاز + القفل المحلي · قاعدة مشفرة · **Outbox + Sync push/pull هيكليًا** · الكاميرا المقيدة + hash · الوقت الموثوق (عينات المعايرة) |
| Web | الهيكل · RTL · i18n · تسجيل الدخول · إدارة المستخدمين والأدوار · عارض سجل التدقيق |
| Infra | Docker Compose للتطوير + staging · PostgreSQL + PostGIS + pgaudit + أدوار القاعدة · S3 مع Object Lock · Keycloak realm · المراقبة الأساسية · النسخ الاحتياطي + **أول تمرين استعادة** |
| حوكمة | DPIA مبدئي · مسودة سياسة الاحتفاظ · تحديد المدقق المستقل · تحديد المنطقة التجريبية |

**Definition of Done — Phase 0:**
- [ ] مستخدم يسجل الدخول (Web بـ MFA، Mobile بجهاز مسجل) ويرى فقط ما يسمح به دوره.
- [ ] منح دور حساس يتطلب Checker، ومنح الذات مرفوض، وSoD الثابت مرفوض — **باختبارات آلية**.
- [ ] أمر تجريبي من الموبايل دون اتصال يصل بعد الاتصال مرة واحدة فقط (Idempotent) مع وقت مقدر صحيح رغم تغيير ساعة الجهاز.
- [ ] صورة ملتقطة داخل التطبيق تصل بـ `HASH_OK` إلى Bucket بـ Object Lock؛ صورة معدلة ← `HASH_MISMATCH`.
- [ ] كل تغيير في Phase 0 ينتج حدث تدقيق في نفس المعاملة؛ محاولة UPDATE/DELETE على التدقيق تفشل؛ `chain-verifier` يكتشف تعديلًا يدويًا مُحقونًا في الاختبار.
- [ ] Checkpoint يومي يُكتب في Bucket التثبيت.
- [ ] تمرين استعادة ناجح وموثق.
- [ ] CI أخضر بكل الفحوص؛ لا أسرار في المستودع.
- [ ] نموذج التطبيق الميداني اختُبر مع فنيين حقيقيين، ونتائج الاختبار موثقة ومطبقة على التصميم.
- [ ] الأسئلة المفتوحة (16.5) مُجابة وموثقة في ADRs.

### PHASE 1 — Street Light Vertical Slice (≈ 12–16 أسبوعًا بناء + 8 أسابيع تجربة)

**الهدف:** إثبات المسار الكامل على بيانات وأشخاص حقيقيين:

```
Create Asset → Verify → QR bind → Issue (patrol) → Work Order → Assign
→ Arrive (scan + before) → Diagnosis → Start → Consume from custody (+ serial, core)
→ Checklist + test → After → Submit → Review (+ checker) → Close + Seal
→ Rules/Recommendations → Dashboard → Audit trail + random audit
```

**التسلسل الداخلي (كل خطوة قابلة للعرض):**

| Sprint (أسبوعان) | المحتوى |
|---|---|
| 1 | أنواع الأصول (Light Point، Feeder Pillar) + JSON Schema · Tags (دفعات، طباعة PDF، عهدة) · تسجيل أصل من الموبايل (دون اتصال) |
| 2 | طابور الاعتماد (Web) · العينة الميدانية · التحقق الميداني (Mobile) · إصدار Asset Code · الخريطة الأساسية |
| 3 | البلاغات + التأكيد + جولة التفقد (Mobile) · إنشاء وإسناد أوامر العمل (Web) · آلة حالات أمر العمل كاملة + اختبارات property-based |
| 4 | معالج الفني: الوصول، قبل، التشخيص، البدء · درجة الحضور · قوالب الفحص |
| 5 | المخزون: الأصناف، المواقع، Ledger، الطلب/الصرف/التأكيد، العهدة، الاستهلاك، الأرقام التسلسلية، Core Return، الإرجاع |
| 6 | الفحص، بعد، التقديم · شاشة المراجعة · Checker · الإرجاع · الختم (Seal) · مصفوفة تعارضات المزامنة + الحجر |
| 7 | قواعد MVP + الإشارات + التوصيات · التدقيق العشوائي المكتبي · لوحة المدير · لوحة المدقق (سلسلة الأدلة) · الجرد (افتتاحي + مفاجئ) |
| 8 | تقوية: أداء على أجهزة ضعيفة، اختبارات المزامنة الكاملة، E2E، اختبار الاختراق، إصلاحات، التدريب، Runbooks |

**التجربة (8 أسابيع):**
- الأسبوعان 1–2: الجرد الأساسي للمنطقة + الجرد الافتتاحي للمخزن + تدريب.
- الأسابيع 3–8: التشغيل الكامل بالتوازي مع الإجراء الحالي في أول أسبوعين ثم النظام وحده.
- مراجعة أسبوعية: زمن الخطوات، الأخطاء، الإشارات ودقتها، ملاحظات الفنيين.

**Definition of Done — Phase 1:**
- [ ] **كل** خطوات المسار أعلاه تعمل على أجهزة حقيقية في الميدان، بما فيها دون اتصال.
- [ ] الجرد الأساسي للمنطقة التجريبية مكتمل ومعلن مغلقًا، مع تقرير الفرق عن البيانات القديمة.
- [ ] صفر فقدان أدلة طوال التجربة (مُثبت بالمطابقة).
- [ ] صفر انتهاك SoD ناجح؛ اختبار المصفوفة 100% أخضر.
- [ ] سلسلة التدقيق سليمة يوميًا + فحص الاتساق الليلي (Seal + أرصدة) بلا فروقات غير مفسرة.
- [ ] كل حالات الإساءة (AC) ذات الضابط التقني في نطاق Phase 1 لها اختبار أخضر.
- [ ] وسيط الوقت الإضافي على الفني ≤ 3 دقائق لأمر عمل روتيني — **أو** خطة تبسيط معتمدة إذا تجاوزناه.
- [ ] ≥ 90% من التقديمات الأولى مكتملة الأدلة.
- [ ] دقة كل قاعدة Flag مقاسة من التدقيق العشوائي؛ القواعد الضعيفة معدلة أو معطلة (بقرار Four-Eyes).
- [ ] مؤشرات خط الأساس مقابل التجربة موثقة (MTTR، الأعمدة المطفأة، فروقات المخزون) — مع شرح "مفارقة الإبلاغ".
- [ ] اختبار اختراق مستقل بلا نتائج حرجة/عالية مفتوحة.
- [ ] تمرين استعادة ناجح أثناء التجربة.
- [ ] **شروط تنظيمية:** المدقق من جهة مستقلة ✓ · الجولة الليلية من غير فريق الإصلاح (أو بتدوير) ✓ · سياسة الإبلاغ عن فقد الأجهزة ✓ · DPIA معتمد ✓.
- [ ] تقرير التجربة: ما نجح، ما فشل، ما يجب تغييره قبل التوسع — **وقرار Go/No-Go موثق** من الجهة.

### PHASE 2 — Integrity + Inventory (≈ 4–5 أشهر)

**يبدأ فقط بعد Go من Phase 1.** الأولويات تُعاد ترتيبها حسب نتائج التجربة.

| المجال | المحتوى |
|---|---|
| مراجعة حسب المخاطرة | مراجعة مختصرة لـ LOW؛ مقاييس زمن المراجعة |
| التدقيق | زيارات ميدانية للتدقيق العشوائي · تحليل المراجعين والمديرين (بعد موافقة قانونية/HR) · قواعد Phase 2 في [11 §11.4](11-analytics-rules.md#114-قواعد-phase-2) |
| المخزون المتقدم | تعدد المخازن والتحويلات · التنبؤ · حدود العهدة المتقدمة · تجميع القطع للضمان |
| الأدلة | توقيع الجهاز (Keystore) · قراءة QR من الصورة آليًا · Play Integrity / كشف الجذر |
| الأصول | Health Score مع مؤشر الثقة · توصيات الاستبدال · **الصيانة الوقائية المجدولة** وجولات التفقد المجدولة |
| العمل الميداني | المهمة الذاتية العاجلة دون اتصال · تحسينات المزامنة من دروس التجربة |
| المقاولون | الجهة المنفذة الخارجية، الإغلاق النهائي لمفتش البلدية |
| التوسع | مناطق إضافية للإنارة |

**Definition of Done — Phase 2:**
- [ ] الإنارة تعمل في ≥ 3 مناطق أو البلدية كاملة.
- [ ] زيارات التدقيق الميداني منفذة شهريًا بنتائج موثقة.
- [ ] Health Score معروض مع التفسير والثقة، ومعاير مقابل قرارات المهندسين على عينة.
- [ ] فروقات جرد العهدة المفاجئ في انخفاض مقاس مقابل خط الأساس.
- [ ] أحمال المراجعة للمشرفين ضمن حد مقبول (يُحدد) دون انخفاض جودة (مقاس بالتدقيق العشوائي).
- [ ] موافقة قانونية مكتوبة على تحليلات الأداء الفردي قبل تفعيلها.

### PHASE 3 — Additional Municipal Assets (≈ 6–9 أشهر، تدريجي)

**الترتيب المقترح حسب التشابه مع الإنارة (الأسهل أولًا):**

1. **إشارات المرور** — نقطية، كهربائية، مشابهة جدًا للإنارة. (اختبار أن "إضافة نوع أصل" تهيئة لا برمجة.)
2. **المضخات والمولدات الثابتة** — نقطية، لكن **صيانة وقائية بالساعات** وقراءات (ضغط، حرارة) في الفحص.
3. **المركبات والمعدات المتنقلة** — فئة Mobile Asset: عدادات، ورشة، لا موقع ثابت.
4. **المباني والحدائق** — Facility بأصول فرعية.
5. **الطرق، التصريف، خطوط المياه** — **Linear Assets** بـ Segments و Linear Referencing؛ الأكثر تعقيدًا.
6. **النفايات** — حاويات (نقطية كثيرة ومتنقلة جزئيًا) + مسارات جمع (قد تكون منتجًا مختلفًا أصلًا).

**عمل تمكيني قبل البدء:** تحويل نوع الأصل، قوائم التشخيص، قوالب الفحص، الأدلة المطلوبة، ومستوى المخاطرة إلى **تهيئة كاملة بإصدارات** مع أداة إدارية (Four-Eyes على نشر نسخة قالب).

**DoD لكل نوع أصل جديد:** نفس مسار Vertical Slice كاملًا لهذا النوع + تجربة في منطقة واحدة + لا تغيير في Core الكود إلا في نقاط تمديد موثقة.

### PHASE 4 — Government Integrations (≈ حسب الجهات)

| التكامل | الاتجاه | الملاحظة |
|---|---|---|
| الهوية الوطنية / SSO حكومي | ← | اتحاد في Keycloak؛ لا تغيير في التطبيق |
| GIS رسمي | ↔ | تصدير الأصول (OGC API Features / WFS) واستيراد الطبقات المرجعية؛ **نحن لسنا مصدر الحقيقة للخرائط الأساسية** |
| ERP / المالية | → | ترحيل تكاليف الصيانة المعتمدة (Closed WOs) كقيود؛ **اتجاه واحد** مبدئيًا |
| المشتريات | ← | أوامر الشراء والاستلام؛ الأسعار الفعلية بدل Standard cost |
| بوابة المواطنين | ← | بلاغات المواطنين مع إزالة التكرار ("1 Issue confirmed by N") + متابعة الحالة |
| الشفافية العامة | → | مؤشرات مجمعة غير حساسة، بعد سنة من جودة بيانات مثبتة |

**المبادئ:** `/integration/v1` منفصل، OAuth2 Client Credentials بنطاقات دقيقة، Webhooks موقعة، Outbox للأحداث الخارجية، سجل تدقيق لكل استدعاء تكامل، ولا وصول مباشر للقاعدة لأي نظام خارجي.

### PHASE 5 — Advanced Analytics / Predictive Maintenance

**شرط البدء:** ≥ 18–24 شهرًا من بيانات نظيفة لنوع أصل واحد على الأقل، مع جودة بيانات مقاسة.

- تحليل البقاء (Survival analysis) لأعمار المكونات حسب الطراز/المورد ← **Procurement Intelligence** (تكلفة دورة الحياة لكل طراز).
- التنبؤ بالأعطال على مستوى الدائرة/المنطقة.
- تحسين جدولة الصيانة الوقائية.
- كشف الشذوذ متعدد المتغيرات **كمساعد للمدقق فقط**، مع نفس مبادئ القابلية للتفسير وعدم الحكم الآلي.
- ربما: وحدة تحليلات منفصلة (Python) تقرأ من نسخة تحليلية (Read replica / Data warehouse) — أول فصل حقيقي من الـ Monolith.

## 16.4 ما لن يُبنى (What should NOT be built)

**أبدًا (في هذا المنتج):**
- Blockchain / دفتر موزع.
- تتبع GPS مستمر للموظفين.
- تصنيف آلي للموظفين (Ranking "الأسوأ أداء") أو أي عقوبة آلية.
- حذف السجلات التشغيلية أو التدقيقية.
- نظام ERP / محاسبة / رواتب / مشتريات كامل.
- منصة GIS كاملة (تحرير، تحليل مكاني حر، إدارة طبقات عامة).

**ليس الآن (مؤجل بقرار):**
- Microservices.
- AI chatbot / مساعد ذكي.
- Predictive AI (حتى Phase 5 وشرط البيانات).
- IoT / حساسات / أنظمة التحكم الذكي بالإنارة (CMS) — قد تأتي كتكامل لاحقًا (مصدر بلاغات آلي — مفيد جدًا للإنارة الذكية).
- NFC / RFID / Beacons.
- تطبيق المواطنين.
- أدوار مخصصة ينشئها العميل.
- iOS (إلا إذا فرضته الأجهزة المتاحة).
- لوحات BI مخصصة / منشئ تقارير حر — تصدير CSV مراقب يكفي في MVP.
- تعدد اللغات بعد العربية والإنجليزية.
- تحديات التصوير العشوائية.
- Redis، Kafka، Kubernetes، أي Message broker خارجي.
