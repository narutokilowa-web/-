# 03 — الأدوار ونموذج الصلاحيات

## 3.1 الأدوار

| الدور | المسؤولية | النطاق النموذجي | الواجهة الأساسية |
|---|---|---|---|
| **Field Technician** فني ميداني | تنفيذ أوامر العمل، جمع الأدلة، استهلاك المواد من عهدته، الإبلاغ عن أعطال يكتشفها | فريقه / منطقته | Mobile |
| **Field Inspector** مفتش ميداني | جولات التفقد (الليلية)، إنشاء البلاغات، التحقق الميداني من الأصول، زيارات التدقيق الميدانية | منطقة / قسم | Mobile |
| **Supervisor** مشرف | فرز البلاغات، إنشاء وإسناد أوامر العمل، مراجعة وإغلاق/إرجاع، طلب المواد لفريقه | فريق / منطقة | Web (+ Mobile عرض) |
| **Asset Registrar** مسجّل أصول | مسح وتسجيل الأصول (الجرد والجديد)، ربط الملصقات | منطقة مسح | Mobile |
| **Asset Approver** معتمد أصول | مراجعة واعتماد/رفض تسجيل الأصول وتعديلاتها | قسم | Web |
| **Warehouse Officer** أمين مخزن | الاستلام، الصرف للعهدة، الإرجاع، الجرد، استلام القطع التالفة | مخزن محدد | Web (+ Mobile لاحقًا) |
| **Procurement Officer** موظف مشتريات | تعريف الأصناف والتكلفة المعيارية، استلام الشحنات (Receipts)، عرض التنبؤ | الجهة | Web |
| **Department Manager** مدير قسم | لوحة المؤشرات، الموافقات عالية القيمة (Checker)، شطب الأصول، Break Glass | قسم | Web |
| **Auditor** مدقق | قراءة كل شيء في نطاقه، إدارة الإشارات (Flags)، تنفيذ التدقيق العشوائي، التحقق من سلسلة السجل | الجهة (مستقل) | Web |
| **System Administrator** مدير نظام | المستخدمين، الأجهزة، التهيئة، القوالب | الجهة | Web |

**ملاحظات تصميمية:**
- **الدور ≠ الشخص.** شخص واحد قد يحمل دورين (مشرف + مفتش في بلدية صغيرة) **إلا إذا منع ذلك SoD ثابت** (انظر 3.4).
- دور **Contractor Technician / Contractor Supervisor** مخطط لـ Phase 2: نفس صلاحيات الفني/المشرف لكن نطاقه "جهة منفذة" خارجية، والإغلاق النهائي لمفتش البلدية دائمًا.
- **مدير النظام لا يملك أي صلاحية تشغيلية.** لا يستطيع إغلاق أمر عمل، ولا اعتماد أصل، ولا صرف مواد. مهمته تقنية فقط.

## 3.2 نموذج الصلاحيات: RBAC + نطاق + قواعد سجل

قرار الصلاحية لأي عملية يمر بثلاث طبقات بالترتيب:

```
1. RBAC      : هل يملك أحد أدواره Permission = "workorders.review.approve"؟
2. Scope     : هل السجل (أمر العمل) داخل نطاق إسناد الدور (القسم/المنطقة/الفريق)؟
3. Policies  : قواعد على مستوى السجل (ABAC-lite):
               - SoD الديناميكي: هل هو نفس منفّذ أمر العمل؟ → رفض
               - عتبات: هل التكلفة > حد صلاحيته؟ → يتطلب Checker
               - الحالة: هل أمر العمل في حالة PENDING_REVIEW؟
```

**لماذا ليس ABAC كاملًا (مثل OPA/Cedar) من البداية؟**
- ABAC كامل يضيف محرك سياسات ولغة وتعقيد اختبار. احتياجنا الحقيقي: RBAC + نطاق + ~15 قاعدة سياسة محددة. هذه تُكتب ككود مختبر في طبقة واحدة (`Authorization Policies`).
- التصميم يعزل هذه الطبقة خلف واجهة واحدة `IAuthorizer.Authorize(actor, action, resource)` — لو احتجنا محرك سياسات لاحقًا، نستبدل التنفيذ لا الاستدعاءات.

**صيغة الصلاحية:** `module.resource.action` — مثل `assets.registration.approve`, `inventory.adjustment.request`.
الأدوار هي حزم صلاحيات **مُعرّفة في الكود ومُهيأة بالبذور (Seed)**؛ الجهة لا تنشئ أدوارًا عشوائية في MVP (يمنع خلق دور "خارق" بالتهيئة). تخصيص الأدوار مؤجل لـ Phase 3 مع قيود SoD تلقائية.

**Role Assignment** = (User, Role, ScopeType, ScopeId, ValidFrom, ValidTo, GrantedBy, ApprovedBy).
التواريخ تسمح بإسناد مؤقت (مشرف بديل أثناء إجازة) ينتهي تلقائيًا.

**الملاحظات:**
1. لا يستطيع التحقق أو الاعتماد من سجّل الأصل نفسه (SoD ديناميكي).

7. Break Glass لمدير النظام محصور في الإجراءات التقنية (فك قفل حساب، إعادة تعيين جهاز)، ولا يعطي صلاحيات تشغيلية.

## 3.4 فصل المهام (Separation of Duties)

### SoD ثابت (Static) — أدوار لا تجتمع لنفس الشخص في نفس النطاق

| الدور A | الدور B | السبب |
|---|---|---|
| Asset Registrar | Asset Approver | يسجل ويعتمد لنفسه |
| Warehouse Officer | Field Technician | يصرف لنفسه |
| Warehouse Officer | Procurement Officer | يستلم ما يشتريه |
| Auditor | أي دور تشغيلي | يدقق عمله |
| System Administrator | أي دور تشغيلي (موافقات) | يمنح نفسه ويعمل |

النظام **يرفض** إسناد الدور المتعارض. استثناء (بلدية صغيرة جدًا): يتطلب Break Glass إداري موثق وتنبيهًا دائمًا للمدقق، ويظهر في لوحة المدقق كاستثناء قائم.

### SoD ديناميكي (Dynamic) — على مستوى السجل

| القاعدة | المثال |
|---|---|
| المنشئ ≠ المعتمد | مسجّل الأصل ≠ معتمده؛ طالب التسوية ≠ معتمدها |
| المنفذ ≠ المراجع | الفني الذي نفذ ≠ من يغلق (حتى لو كان المشرف قد نفذ بنفسه كاستثناء) |
| الطالب ≠ الصارف ≠ المستلم | طلب المواد: الطالب، أمين المخزن، والمستلم أطراف مختلفة (الطالب = المستلم مسموح) |
| Maker ≠ Checker | في كل Four-Eyes |
| المُبلّغ ≠ المنفذ | **فقط** للمهام التي تتجاوز عتبة قيمة المواد أو تحتوي قطعًا عالية القيمة (انظر AC-05) |
| لا منح للذات | لا يمنح أحد نفسه دورًا أو يمدد صلاحيته |

## 3.5 Four-Eyes (Maker / Checker) — محرك موافقات عام

بدلًا من برمجة موافقة لكل حالة، **كيان `ApprovalRequest` عام**:

```
ApprovalRequest
  type            : ASSET_DECOMMISSION | ASSET_CHANGE | STOCK_ADJUSTMENT | HIGH_VALUE_ISSUE
                    | WO_HIGH_COST_CLOSE | POST_CLOSURE_AMENDMENT | ROLE_GRANT | CONFIG_CHANGE ...
  subject_ref     : (entity_type, entity_id, version)
  proposed_change : JSON (الحالة/القيم المقترحة) + hash
  maker           : user, reason, timestamp
  checker_policy  : من يحق له الموافقة (دور + نطاق + استثناء المنشئ)
  status          : PENDING → APPROVED | REJECTED | EXPIRED | WITHDRAWN
  decision        : checker, reason, timestamp
```

**قاعدة حرجة:** التغيير المقترح **لا يُطبق** إلا بعد الموافقة، ويُطبق على **نفس الإصدار** (Version) الذي رآه المعتمد. إذا تغير السجل بين الطلب والموافقة → يُبطل الطلب تلقائيًا (يمنع "وافقت على شيء، وطُبق شيء آخر").

**العتبات** (قابلة للتهيئة بموافقة Four-Eyes نفسها):
- قيمة مواد أمر عمل > X ← إغلاق يتطلب مدير قسم.
- صرف صنف بكمية > Y أو قيمة > Z (أو تراكمي خلال 7 أيام) ← Checker.
- أي تسوية جرد سالبة ← Checker؛ فوق W ← + إشعار مدقق.
- **تغيير معاملات قواعد التحليل أو تعطيلها** ← Maker: مدير قسم، Checker: **مدقق** (يمنع المدير من إسكات قاعدة تزعجه).

## 3.6 Break Glass

```
طلب → سبب إلزامي (نص + تصنيف) → نطاق (ما الذي يُفتح) → مدة (افتراضي 2 ساعة، أقصى 8)
   → تفعيل فوري (لا ينتظر موافقة — لأنه طارئ)
   → تنبيه فوري للمدقق + مدير الجهة
   → كل عملية أثناء الجلسة موسومة break_glass_session_id
   → انتهاء تلقائي
   → مراجعة لاحقة إلزامية من المدقق (مطلوب تقرير خلال 72 ساعة)
```

ما **لا** يفتحه Break Glass أبدًا: حذف السجلات، تعديل سجل التدقيق، تعطيل التدقيق، تجاوز SoD "المنفذ ≠ المراجع" على نفس السجل.

## 3.7 إدارة الهوية

- **Keycloak** (OIDC) لإدارة الهوية (انظر [08](08-architecture-and-technology.md) للسبب).
- **MFA إلزامي** لـ: مدير قسم، معتمد، مدقق، مدير نظام، مشتريات، مخزن.
- الفنيون: تسجيل دخول مرتبط بالجهاز المسجل + قفل محلي (بصمة/PIN). MFA عند تسجيل جهاز جديد فقط.
- **الصلاحيات تُقيّم في Backend من قاعدة البيانات**، لا من الـ Token. الـ Token يحمل الهوية فقط. (يمنع صلاحيات قديمة في Token صالح لساعة بعد سحب الدور.)
- المستخدم يُعطّل ولا يُحذف (تاريخه جزء من السجل).
