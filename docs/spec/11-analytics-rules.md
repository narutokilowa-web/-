# 11 — قواعد التحليلات والتوصيات

## 11.1 إطار القواعد

كل قاعدة:
- **مُصدَّرة** (`rule_versions`) بمعاملات قابلة للتهيئة، وتغيير المعاملات = Four-Eyes (مدير قسم + مدقق). **العتبات لا تُنشر للمستخدمين الميدانيين** (Goodhart).
- **تنتج أحد ثلاثة:** `Recommendation` (تشغيلية، على أصل) · `AuditFlag` (نزاهة، على كيان) · `Notification` (تنبيه تشغيلي).
- **تحمل تفسيرها** (`explanation`): المدخلات، العتبة، القيمة المحسوبة، رابط للبيانات الخام.
- **لها مالك ومقياس دقة:** نسبة ما أُكّد من إشاراتها (Precision) — تُراجع شهريًا.
- **تُطبق في وقت محدد:** فورية (عند حدث) أو دورية (ليلية).
- **لها حد أدنى للعينة** حيث تعتمد على الإحصاء.

**لا ML في هذه المرحلة.** القواعد SQL/كود بسيط مختبر، يمكن لأي مدقق فهمه.

## 11.2 تعريفات أساسية (يجب الاتفاق عليها قبل أي قاعدة)

| المصطلح | التعريف |
|---|---|
| **عطل (Failure)** | أمر عمل تصحيحي مغلق على الأصل كـ **Primary Asset** بتشخيص ليس `NFF` ولا `SUPPLY_FAULT_UPSTREAM` ولا `ASSET_NOT_FOUND`. التخريب والحوادث **تُحسب منفصلة** (ليست عيبًا في الأصل). |
| **انقطاع خارجي** | الأصل في `wo_affected_assets` — لا يُحسب عطلًا له |
| **إعادة عمل (Rework)** | عطل جديد على نفس الأصل خلال 30 يومًا من إغلاق سابق بنفس التشخيص أو تشخيص مرتبط |
| **تكلفة الصيانة** | Σ (مواد × Standard cost وقت الاستهلاك) + Σ (ساعات العمل × معدل الفئة) + (ساعات المعدات × معدلها) |
| **Downtime** | من أول بلاغ مؤكد إلى إغلاق ناجح (أو اختبار ليلي ناجح) |

## 11.3 قواعد MVP (Phase 1)

| الكود | النوع | الشرط | الناتج | توقيت |
|---|---|---|---|---|
| `R-REC-FAIL` | Recommendation | ≥ 3 أعطال خلال 180 يومًا | "فحص شامل" — مع قائمة الأعطال وتشخيصاتها | عند الإغلاق |
| `R-REWORK` | Recommendation + مؤشر | إعادة عمل خلال 30 يومًا | ربط أمري العمل؛ "مراجعة جودة الإصلاح السابق" | عند الإنشاء |
| `R-AREA` | Recommendation | ≥ N (افتراضي 4) أصول من نفس الدائرة (`circuit_ref`) أو نفس اللوحة أصبحت FAULTY خلال 48 ساعة؛ **بديل** عند غياب الدائرة: ≥ N ضمن 150م | "افحص اللوحة/المغذي قبل إصلاح الأعمدة منفردة" + اقتراح دمج البلاغات في أمر عمل واحد على اللوحة | عند البلاغ |
| `R-WARRANTY` | Recommendation | عطل على أصل `warranty_until > today` بتشخيص عيب مصنعي | "مطالبة ضمان محتملة" | عند التشخيص |
| `R-LOW-STOCK` | Notification | رصيد (مخزن + عهد) < `reorder_point` | تنبيه للمخزن والمشتريات | يومي |
| `R-OVERDUE` | Notification | أمر عمل تجاوز `sla_due_at` | تنبيه المشرف، ثم المدير بعد 2× | كل ساعة |
| `R-PHOTO-DUP` | Flag (حرج) | sha256 مطابق لدليل سابق | رفض الدليل + Flag | عند الرفع |
| `R-PHOTO-SIM` | Flag | pHash بمسافة Hamming ≤ 6 مع دليل **من مهمة أخرى** | Flag مع الصورتين جنبًا لجنب | عند الرفع |
| `R-HASH-MISMATCH` | Flag (حرج) | الملف لا يطابق hash الأمر | Flag | عند الرفع |
| `R-PRESENCE-WEAK` | Flag | درجة الحضور < 40 | رفع مستوى المخاطرة | عند الوصول |
| `R-MOCK-GPS` | Flag | `is_mock = true` | | عند الوصول |
| `R-CONSUME-CUSTODY` | Flag | استهلاك > رصيد العهدة / رقم تسلسلي مجهول | | عند المزامنة |
| `R-ISSUE-UNCONFIRMED` | Flag | صرف غير مؤكد > 24 ساعة | | كل ساعة |
| `R-CORE-MISSING` | Flag | التزام Core Return مفتوح > 7 أيام | | يومي |
| `R-NFF-RECHECK` | Notification | NFF أو "لم يُختبر وظيفيًا" | إدراج الأصل في الجولة الليلية التالية | عند الإغلاق |
| `R-ASSET-NOT-FOUND` | Flag (حرج) | تشخيص ASSET_NOT_FOUND | الأصل ← UNDER_INVESTIGATION | فوري |
| `R-DUP-WORK` | Flag | أمرا عمل مغلقان لنفس الأصل ونفس التشخيص خلال 7 أيام | | عند الإغلاق |
| `R-POST-CLOSE` | Flag (معلومة) | أي Amendment | يظهر للمدقق | فوري |
| `R-BREAK-GLASS` | Flag | أي جلسة Break Glass | Audit case تلقائي | فوري |

## 11.5 Health Score (Phase 2) — تصميم قابل للتفسير

```
score = 100
  − age_penalty          : min(25, 25 × age / expected_life)      [يُحذف إذا العمر UNKNOWN → confidence↓]
  − failure_penalty      : min(30, 10 × failures_last_12m)
  − rework_penalty       : min(15, 7.5 × reworks_last_12m)
  − cost_penalty         : min(20, 20 × cost_12m / replacement_cost)
  − downtime_penalty     : min(10, 10 × downtime_days_12m / 30)
  − overdue_inspection   : 5 إذا لم يُفحص خلال فترة الفحص المحددة لنوعه
clamp(0, 100)

confidence = HIGH   إذا: عمر معروف + ≥ 12 شهرًا في النظام + فحص خلال 6 أشهر
           = MEDIUM إذا: أحد الشروط ناقص
           = LOW    إذا: عمر مجهول و < 6 أشهر في النظام
```

**العرض دائمًا مفصل:**
```
صحة الأصل: 42/100   (ثقة البيانات: متوسطة)
  −18  العمر: 9 من 12 سنة متوقعة
  −30  3 أعطال خلال 12 شهرًا (DRIVER ×2، CABLE ×1)
  −10  تكلفة الصيانة 50% من تكلفة الاستبدال
توصية: مراجعة الاستبدال
```

الأوزان **مبدئية وتُعاير** بعد 6 أشهر من البيانات بمقارنتها مع قرارات المهندسين الفعلية.

## 11.6 مؤشرات اللوحات (Metrics)

| المؤشر | التعريف | المستوى |
|---|---|---|
| الأصول المسجلة / المقدرة | % تغطية الجرد لكل منطقة | إدارة |
| الأصول المعطلة الآن | `operational_status ∈ {FAULTY, OUT_OF_SERVICE}` | إدارة، مشرف |
| أوامر العمل المفتوحة / المتأخرة | حسب الأولوية والعمر | مشرف |
| MTTR | وسيط `CLOSED − Issue.created` (الوسيط لا المتوسط — القيم الشاذة كثيرة) | إدارة |
| نسبة الإصلاح من المرة الأولى | 1 − (Rework / أعطال) | إدارة |
| التكلفة لكل أصل / لكل نوع / لكل منطقة | | إدارة |
| الأعطال المتكررة | عدد الأصول بـ R-REC-FAIL مفتوح | إدارة |
| طابور الموافقات | عدد وعمر الطلبات المعلقة **لي** | الكل |
| تحذيرات المخزون | | مخزن، مشتريات |
| الإشارات المفتوحة | حسب الخطورة والعمر | مدقق (والمدير: إشارات الأصول/العمليات فقط) |
| نسبة الأدلة المكتملة عند التقديم | جودة البيانات | مشرف |
| زمن الوصول للأدلة (Upload lag) | صحة المزامنة | تقني |

**كل مؤشر قابل للنقر** وصولًا للسجلات الخام التي أنتجته — لا أرقام يتيمة.
