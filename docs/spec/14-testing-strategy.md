# 14 — استراتيجية الاختبار

## 14.1 المبدأ

في هذا المنتج، **الخطأ الأخطر ليس انهيار الشاشة، بل انتقال حالة غير مسموح أو صلاحية مسربة أو دليل مفقود.** لذلك يتركز الاستثمار في اختبار **منطق النطاق، الصلاحيات، المزامنة، والنزاهة** — لا في تغطية الواجهات.

## 14.2 الطبقات

| الطبقة | الأدوات | ما تغطيه | الحد الأدنى |
|---|---|---|---|
| **Unit — النطاق** | xUnit + FluentAssertions | آلات الحالات، الحسابات (درجة الحضور، الوقت المقدّر، الأرصدة، القواعد)، التحقق | 90%+ لـ Domain في وحدات WorkOrders/Inventory/Assets/Audit |
| **Property-based** | FsCheck (أو CsCheck) | آلات الحالات: أي تسلسل عشوائي من الأوامر لا يصل لحالة غير صالحة · المخزون: الرصيد = مجموع الحركات دائمًا ولا يُنشأ مخزون من العدم · السلسلة: أي تعديل على أي حدث يُكتشف | إلزامي لآلات الحالات الأربع والـ Ledger والسلسلة |
| **Architecture** | NetArchTest | لا وحدة تستخدم Infrastructure وحدة أخرى · لا وصول لجداول وحدة أخرى · Domain لا يعتمد على Infrastructure | يفشل البناء |
| **Integration** | Testcontainers (PostgreSQL+PostGIS، S3 محلي، Keycloak) | المعاملات (تغيير + تدقيق معًا أو لا شيء)، القيود في القاعدة (الـ Trigger يرفض UPDATE على التدقيق)، RLS، الاستعلامات المكانية، Outbox | كل Endpoint أمر على الأقل مسار ناجح + فاشل |
| **Authorization matrix** | مولّد من ملف المصفوفة (YAML) | **كل (دور × عملية × نطاق داخل/خارج)** — يتوقع 200/403 بالضبط كما في [03](03-roles-and-permissions.md) + كل قواعد SoD الديناميكية | 100% من المصفوفة — المصفوفة هي مصدر الحقيقة للكود والوثيقة والاختبار معًا |
| **Abuse cases** | Integration | كل حالة AC-01…AC-33 من [02](02-threat-and-abuse-analysis.md) كسيناريو: هل يُمنع؟ هل يُكتشف؟ هل تظهر الإشارة الصحيحة بالشرح الصحيح؟ | 100% من الحالات التي لها ضابط تقني |
| **Sync scenarios** | محاكي أجهزة في .NET يستدعي Sync API | انظر 14.3 | 100% من المصفوفة في [10](10-offline-sync.md#105-مصفوفة-حل-التعارضات-domain-level) |
| **Contract** | OpenAPI diff في CI | لا تغيير كاسر للـ API دون رفع الإصدار · العملاء المولدون (TS/Dart) تُبنى بنجاح | يفشل البناء |
| **Mobile** | Flutter unit + widget + integration_test | منطق الـ Outbox والترتيب والتشفير المحلي · المعالج خطوة بخطوة · العمل دون اتصال (وضع الطيران) | المسارات الأساسية |
| **Web E2E** | Playwright | المسارات الحرجة لكل دور · RTL بصريًا (لقطات) | ~15 سيناريو |
| **Audit chain** | أداة `chain-verifier` + اختبارات | توليد سلسلة → تعديل حدث/حذف حدث/إعادة ترتيب → يُكتشف · مطابقة التثبيت الخارجي | إلزامي |
| **Performance** | k6 | Sync push لـ 50 جهاز متزامن بعد يوم دون اتصال · الخريطة بـ 30k أصل · لوحة المدير < 2 ثانية | قبل التجربة |
| **Security** | SAST (CodeQL/Semgrep)، DAST (OWASP ZAP على staging)، فحص التبعيات والصور، اختبار اختراق مستقل | ASVS L2 | قبل الإنتاج |
| **Backup/restore** | Runbook آلي | استعادة كاملة إلى بيئة معزولة + `chain-verifier` + اختبار دخان | شهري |

## 14.3 سيناريوهات المزامنة (أمثلة من الحزمة)

| # | السيناريو | المتوقع |
|---|---|---|
| S-01 | فني دون اتصال 30 ساعة، ينجز 4 مهام، يعود | كل الأوامر مطبقة بالترتيب، الأوقات المقدرة صحيحة، لا تكرار |
| S-02 | نفس الدفعة تُرسل 3 مرات (شبكة متقطعة) | نتيجة واحدة، `DUPLICATE` للتكرارات |
| S-03 | إعادة إسناد المهمة أثناء عدم الاتصال | الأدلة والمواد مقبولة، الانتقال لا يُطبق، علامة + إشعار |
| S-04 | إلغاء المهمة أثناء عدم الاتصال | Quarantine بكامل المحتوى |
| S-05 | الفني يقدّم الساعة 3 ساعات للخلف دون اتصال | الأوقات المقدرة صحيحة من `elapsed`، `CLOCK_SKEW` |
| S-06 | إعادة تشغيل الجهاز دون اتصال ثم تعديل الساعة | `time_confidence=LOW`، الاتساق محفوظ، Flag |
| S-07 | انقطاع أثناء رفع صورة 70% | الاستئناف، hash مطابق |
| S-08 | صورة معدلة على الجهاز بعد إرسال الأمر | `HASH_MISMATCH` Flag حرج |
| S-09 | جهاز ملغى يرسل بيانات | Quarantine كامل، حدث أمني |
| S-10 | استهلاك يتجاوز العهدة | مطبق + Flag |

## 14.4 القبول الميداني (UAT + Pilot)

- **UAT في staging** مع مستخدم حقيقي لكل دور، على سيناريوهات مكتوبة (من الإنشاء للإغلاق والتدقيق).
- **اختبار ميداني قصير (أسبوع) قبل التجربة الكاملة:** 2 فنيين، 50 أصلًا، نهارًا وليلًا، شبكة سيئة فعلية.
- **قياسات القبول في التجربة:**
  - زمن التفاعل الإضافي للفني لأمر عمل روتيني ≤ 3 دقائق (وسيط).
  - نسبة الأدلة المكتملة عند أول تقديم ≥ 90%.
  - صفر فقدان أدلة (كل دليل مُعلن عنه وصل بـ HASH_OK أو له سبب موثق).
  - صفر انتهاك SoD ناجح.
  - دقة القواعد: كل قاعدة Flag لها Precision مقاس؛ القواعد < 20% تُعدل.
  - سلسلة التدقيق سليمة يوميًا طوال التجربة.
  - رضا المستخدمين الميدانيين (استبيان قصير + مقابلات) — **إذا كرهوه، سيفشل مهما كانت الأرقام الأخرى.**

## 14.5 "بيانات الاختبار" و"وضع التدريب"

- بذور صناعية واقعية: منطقة بـ 500 أصل، فرق، مخزون، سنة من التاريخ المُولد (لاختبار القواعد والتحليلات).
- **وضع تدريب (Training tenant)** منفصل في staging يستخدمه الفنيون للتدرب دون تلويث بيانات الإنتاج.
